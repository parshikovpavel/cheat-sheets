# Определение таймаута для запроса

Универсального таймаута нет. Его нужно выводить из статистики конкретной зависимости. При расчете таймаута для конкретного запроса можно учесть SLA сервиса.

Правило:

- для статичного таймаута без учета SLA родительского запроса `timeout1 = p99.9 latency зависимости × 1.5–2`
- для статичного таймаута с учетом SLA родительского запроса `timeout2 = SLA на обработку родительского запроса - другие операции в родительском запросе`. Пример: endpoint должен отвечать за 2 секунды. Локальная обработка занимает 300 мс, запас — 200 мс. На зависимость остаётся максимум 1,5 секунды. Даже если её собственный дефолт равен 5 секундам, конкретный вызов должен завершиться примерно за **1,5 секунды**.
- для таймаута в рамках текущего *request*'а `timeout2 = min(оставшийся deadline родительского запрос, timeout1)`

Стартовые значения, если метрик пока нет:

- внутренний сервис в одном дата-центре: **300 мс – 1 с**;
- межрегиональный внутренний сервис: **1–2 с**;
- внешний HTTP API через интернет: **2–5 с**;
- connect timeout: **200–500 мс**;

Для долгих операций лучше использовать асинхронную задачу, а не HTTP-вызов с таймаутом в минуты.

Важно:

- Всегда ставить конечный deadline; не оставлять вызовы без таймаута.
- Разделять connect timeout и общий timeout операции.
- Передавать deadline через `context` в HTTP/gRPC.
- если запрос не уложился в timeout смотри [Ошибка при доступе к сервису](#ошибка-при-доступе-к-сервису)
- Ретраить только временные ошибки: timeout соединения, `502`, `503`, `504`, gRPC `Unavailable`.
- Следить за долей таймаутов и latency p95/p99; слишком короткий timeout создаёт ложные ошибки, слишком длинный — каскадные отказы.
