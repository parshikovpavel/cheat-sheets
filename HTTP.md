HTTP (HyperText Transfer Protocol, протокол передачи гипертекста)

- протокол прикладного уровня. 

- текстовый протокол. Однако с использованием соответствующих заголовков можно указать что в текстовом виде закодированы двоичные данные.

- порт по умолчанию 80

HTTP используется также в качестве «транспорта» для других протоколов прикладного уровня, таких как SOAP, XML-RPC, WebDAV.

Заголовки используются для указания в запросе/ответе характеристик контента: формат, кодировка, язык. 

Протокол HTTP не сохраняет промежуточное состояние между парами «запрос-ответ». При этом клиент и сервер могут самостоятельно осуществлять сохранение информации о состоянии (например, «куки» на стороне клиента, «сессии» на стороне сервера).

Всё программное обеспечение для работы с протоколом HTTP делится на три категории:

- серверы – отвечают за обработку запросов. Для отличия конечных серверов от прокси, в официальной документации используется термин «исходный сервер» (*origin server* [ˈɒrɪʤɪn ˈsɜːvər]).

- клиенты – отправляют запросы

- прокси – посредники

## Термины

### Потентность

#### Нульпотентность

Нульпотентность (*nullipotent* [ˈnʌlˈɪmpətənt]), безопасные методы (*safe method* [seɪf ˈmeθəd]).

Если результат идемпотентной операции при многократном повторении тот же что и при первом, то результат нульпотентной операции тот же что и без ее применения вообще. 

Т.е. нульпотентная операция не имеет побочных эффектов вообще. В то время как идемпотентная операция не имеет дополнительных побочных эффектов после первого применения.

Пример:

- в математике – сложение числа с нулем:

- в протоколе HTTP – нульпотентные *methods* называются безопасными (*safe*). По стандарту это HEAD, GET, OPTIONS и TRACE


- в базах данных – операция SELECT

#### Идемпотентность

Идемпотентность (*idempotence* [aɪˈdɪmpətəns])— свойство операции при нескольких идентичных применениях к объекту давать тот же эффект, что и при одном применении.

Идемпотентная операция не имеет дополнительных побочных эффектов после первого применения и возвращает одно и то же значение.

Это очень полезное свойство операции, так как в этом случае нет необходимости отслеживать, была операция уже выполнена или нет.

Пример:

- в математике – нахождение модуля числа:

- в вебе –в протоколе HTTP *methods* PUT и DELETE являются идемпотентными. 

- в базах данных: операции UPDATE и DELETE являются идемпотентными. При этом операция INSERT не является идемпотентной.

Последовательность идемпотентных операций может быть в целом не идемпотентной. Например, такая последовательность идемпотентных по отдельности операций:

```sql
SELECT value FROM table
UPDATE table SET value=5
SELECT value FROM table
```

в итоге неидемпотентна. Если value изначально равно 3, на первом шаге выводит (3), (5), а на втором шаге (5, 5).]

### *Stateless* протокол

Протокол без сохранения состояния (*Stateless protocol*) — это протокол, для которого взаимодействие клиента с сервером  состоит из независимых соединений типа запрос-ответ.Под состоянием (сессией) подразумевается информация о предшествующем взаимодействим с клиентом. На сервере не сохраняется никакой информации о состоянии клиента. Каждый новый запрос начинается с «чистого листа» и не учитывает предшествующее взаимодействие с клиентом.

*Stateless* протоколу противопоставляется протокол с сохранением состояния (*stateful protocol*). На сервере сохраняется состояние клиента. Эта информация влияет на обработку последующих запросов этого клиента. 

При сетевом взаимодействии в компьютерной системе на различных уровнях могут быть реализованы, как *stateless*, так и *stateful* протоколы. Например, HTTP (*stateless protocol*) работает на основе [TCP](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) (*stateful protocol*), который работает на базе [IP](https://en.wikipedia.org/wiki/Internet_Protocol) (*stateless protocol*), который работает с применением протокола маршрутизации BGP и таблиц маршрутизации (*stateful protocol*).

Такие уровни создаются и выше протокола HTTP, в прикладном приложении. По причине отсутствия сессий в протоколе HTTP, в запросе вместе с cookie передается уникальный идентификатор пользователя, который позволяет серверу отслеживать запросы, исходящие от одного и того же клиента. Таким образом создается *stateful* протокол поверх HTTP.

Примеры *stateless* протоколов:

- Internet Protocol (IP),

- Hypertext Transfer Protocol(HTTP),

Преимущества:

- упрощает архитектуру сервера, потому что нет необходимости работать с сессиями на стороне сервера

- упрощает масштабирование системы, т.к. запросы независимы и могут быть легко распределены по кластеру

Недостаток:

- т.к. сервер не хранит состояния, информация о состоянии клиента должна включаться в каждый запрос.

### Сущность (*entity*)

В запросе и ответе может передаваться сущность (*entity*). Сущность определяется заголовками сущности (*entity-header*) и телом сущности (*entity-body*). К *entity-headers* относятся заголовки Content-XXX, заголовки кеширования.

2015 год.

В HTTP/2 сервер имеет право послать то содержимое, которое ещё не было запрошено клиентом. Это позволит серверу сразу выслать дополнительные файлы, которые потребуются браузеру для отображения страниц, без необходимости анализа браузером основной страницы и запрашивания необходимых дополнений.

## Запрос

### Общая структура

1. Стартовая строка (*Starting line*)
2. Заголовки (*Headers*)
3. Тело сообщения (*Message Body*)

Тело сообщения может отсутствовать, но стартовая строка и заголовки являются обязательными элементами. 

Для HTTP1.1 обязательным является заголовок запроса Host.

Минимальный запрос

```http
GET /index.php HTTP/1.1
Host: localhost
```

Для переноса строки следует использовать символ возврата каретки (*Carriage Return*, CR), за которым следует символ перевода строки (*Line Feed*). После последнего заголовка заголовка CR+LF добавляется дважды. Впрочем веб-сервера корректно обрабатывают одиночный LF без CR (это им рекомендовано в спецификации).

### Стартовая строка

Формат стартовой (начальной) строки запроса:

```text
Метод URI HTTP/Версия
```

 

```http
GET /index.html HTTP/1.1
```

#### Метод

Метод (*method*, *verb*, «глагол») –операция, которую нужно осуществить с указанным ресурсом, одно слово заглавными буквами. Спецификация HTTP 1.1 не ограничивает количество возможных методов, однако для совместимости используются стандартные методы, смысл которых описан в спецификации протокола.

Если серверу не известен указанный клиентом метод, то он должен вернуть статус 501(Not Implemented). Если серверу метод известен, но он неприменим к конкретному ресурсу, то статус ответа 405 (Method Not Allowed). В обоих случаях серверу следует включить в сообщение ответа заголовок Allow со списком поддерживаемых методов.

 

##### OPTIONS

Используется для определения возможностей веб-сервера или параметров соединения для конкретного ресурса. В ответ сервер включает заголовок Allow со списком поддерживаемых методов. Тело запроса и ответа не используется и игнорируется. Как правило используется для определения возможностей всего сервера в формате:

```http
OPTIONS * HTTP/1.1
```

##### GET

Используется для запроса содержимого указанного ресурса. Параметры выполнения запроса передаются в URI целевого ресурса после символа «?»:

```http
GET /path/resource?param1=value1&param2=value2 HTTP/1.1
```

Иногда отдельно выделяют

- Условный GET — содержит заголовки If-Modified-Since, If-Match, If-Range и подобные;

- Частичный GET — содержит в запросе Range.

##### HEAD

Аналогичен методу GET, за исключением того, что в ответе сервера отсутствует тело. Запрос HEAD обычно применяется для извлечения метаданных, проверки наличия ресурса (валидацияURL), даты его последнего изменения.

##### POST

Применяется для передачи пользовательских данных заданному ресурсу. Часто используется при передаче содержимого веб-форм (`<form method="post">`), в том числе для загрузки файлов. Передаваемые данные включаются в тело запроса. 

При результате выполнения 200 (Ok) в тело ответа следует включить сообщение об итоге выполнения запроса. Если был создан ресурс, то серверу следует вернуть ответ 201 (Created) с указанием URI нового ресурса в заголовке Location.

##### PUT

Применяется для загрузки содержимого запроса на указанный в запросе URI. Тело запроса должно содержать модифицированную версию ресурса. Модифицированная версия должна заменить исходный ресурс на *origin* сервере. Если по заданному URI не существует ресурс, то сервер создаёт его и возвращает статус 201 (Created). Если же был изменён ресурс, то сервер возвращает 200 (Ok) или 204 (No Content). 

Ключевое отличие метода POST от метода PUT в функциональном назначении. Метод POST предполагает, что по указанному URI будет производиться обработка передаваемых в теле запроса данных. Метод PUT предполагает, что в теле запроса находится содержимое ресурса, по данному URI.

##### PATCH

Метод PUT для обновления ресурсов имеет ряд недостатков, которые особенно проявляются при использовании REST:

- требуется отправить полное представление всего ресурса с обновленными значениями;

- при обновлении ресурса используется оптимистическая блокировка ресурса. Перед записью модифицированного ресурса требуется сверить версию ресурса, который до этого был получена методом GET, и ресурса, который хранится в данный момент на сервере. Если в промежуток времени между получением ресурса методом GET и его обновление методом PUT вклинился с изменениями другой запрос, то возникает коллизия, отправленные на сервер изменения не фиксируются и возвращается код ошибки. 

- зачастую обновление требуется не всему ресурсу, а только его части. Например, только заголовку поста, а не всему посту.

В теле запроса с методом PATCH содержится набор инструкций, описывающих, каким образом ресурс на *origin* сервере по указанному URI, должен быть изменен для получения новой версии ресурса. 

Пример REST-запроса, который заменяет (replace) email-адрес, добавляет (add) нового друга и копирует (copy) треклист:

```http
PATCH /users/123
```

 

```json
[
   { "op": "replace", "path": "/email", "value": "new.email@example.org" }
   { "op": "add", "path": "/friends", "value": "user_234" }
   { "op": "copy", "from": "/tracklist/1", "path": "/tracklist/2" }
]
```

##### DELETE

Удаляет указанный ресурс.

##### Потентность методов

Идемпотентность (*idempotence*) и безопасность (*safety*) являются основными признаками, отличающими HTTP *methods*.

###### Безопасные методы

Безопасные методы (*safe methods*) или нульпотентные методы не имеют никаких побочных эффектов (если не брать во внимание не влияющие на бизнес-логику эффекты, такие как логгирование, кеширование, выдача рекламных баннеров или инкрементирование веб-счетчика). К этим методам относятся HEAD, GET, OPTIONS и TRACE, эти методы предназначены только для извлечения информации и не изменяют состояние сервера. 

Безопасные методы используются при сканировании поисковыми ботами, чтобы не оказывать воздействие на состояние сервера. 

Несмотря на то что метод GET в стандарте заявлен как безопасный, на практике при обработке GET запросов программистами выполняются побочные действия: create, update, delete. Это может привести к проблемам:

- при кешировании – GET запрос реально не произойдет, т.к. результат будет отдаваться из кеша браузера

- при доступе по ссылке поискового бота –например он может непреднамеренно удалить статью сделав GET-запрос, типа http://example.com/article/1234/delete

###### Идемпотентные методы

Идемпотентные методы (*idempotent methods*) те, которые при нескольких одинаковых запросах имеют тот же эффект, что и при однократном запросе. Под эффектом подразумевается оказываемый запросом побочный эффект, т.е. воздействие на состояние сервера. При этом сам ответ (код ответа, тело ответа) могут отличаться при повторных запросах. К идемпотентным относятся методы PUT и DELETE, т.е. идемпотными являются операции вставки контента по указанному URI и операция удаления. Очевидно, что безопасные (нульпотентные) методы HEAD, GET, OPTIONS и TRACE также являются и идемпотентными.

Запросы PUT и DELETE будут идемпотентными, только в том случае если в URI уникально идентифицируют некоторый ресурс (например, DELETE /post/123). Если URI не идентифицируют уникальный ресурс, например удалить последний пост DELETE post/recent), идемпотентность не гарантируется.

Метод POST не обязательно идемпотентен, и поэтому отправка идентичного запроса POST несколько раз может дополнительно повлиять на состояние сервера и вызвать дополнительные побочные эффекты (например, вставить лишнюю запись). Поэтому пользователь должен быть огражден от повторной отправки POST-запроса. Как правило веб-браузеры в этом случае отображают всплывающее окно с предупреждением и вопросом о необходимости отправки дополнительного запроса.

#### URI

URI (Uniform Resource Identifier, унифицированный идентификатор ресурса) — путь до ресурса (например, скрипта), над которым необходимо осуществить операцию.

Некоторые запросы могут относиться не к какому-либо ресурсу, а к всему серверу, в этом случае вместо URI в стартовую строку добавляется звёздочка (символ «*»). 

```http
OPTIONS * HTTP/1.1
```

#### Код состояния

https://www.codetinkerer.com/2015/12/04/choosing-an-http-status-code.html

Код состояния (*Status Code*) — три цифры (первая из которых указывает на класс состояния), которые определяют результат совершения запроса.

Набор кодов состояния является стандартом, и они описаны в соответствующих документах RFC. Клиент может не знать все коды состояния, но он обязан отреагировать в соответствии с классом кода.

Выделено пять классов кодов состояния.

| Код  | Класс                           | Назначение                                                   |
| ---- | ------------------------------- | ------------------------------------------------------------ |
| 1xx  | Информационный  (informational) | Информирование  о процессе передачи                          |
| 2xx  | Успех (Success)                 | Успешный прием и  обработка запроса клиента                  |
| 3xx  | Перенаправление  (Redirection)  | Для выполнения  операции необходимо сделать еще один запрос по другому URI. Это URI сервер  сервер указывает в заголовке Location. |
| 4xx  | Ошибка клиента   (Client Error) | Означают  наличие ошибки со стороны клиента. В теле сообщения необходимо вернуть  пояснение ошибки в виде HTML. |
| 5xx  | Ошибка сервера (Server Error)   | Означают  наличие ошибки со стороны сервера. В теле сообщения необходимо вернуть  пояснение ошибки в виде HTML. |

##### Информационные

Информирование о процессе передачи

101 Switching Protocols —Сервер отвечает этим кодом на запрос клиента на смену протокола. Новый протокол указывается в запросе и ответе в заголовке Upgrade. Используется для WebSocket. 

##### Успех

Успешный прием и обработка запроса клиента

200 OK — успешный запрос

201 Created — в результате успешного выполнения запроса был создан новый ресурс. Адрес созданного ресурса указывается в заголовке Location.

202 Accepted — запрос был принят на обработку, но она не завершена.

204 No Content — сервер успешно обработал запрос, но в ответе были переданы только заголовки без тела сообщения. Клиент не должен обновлять содержимое документа, но может применить к нему полученные метаданные. 

206 Partial Content — сервер удачно выполнил частичный GET-запрос, возвратив только часть сообщения. В заголовке Content-Range сервер указывает байтовые диапазоны возвращенных данных.

##### Перенаправление

Для выполнения операции необходимо сделать еще один запрос по другому URI. Это URI сервер  сервер указывает в заголовке Location. По стандарту, в Location должен быть указан абсолютный адрес, хотя браузеры понимают и относительный адрес.

Перенаправление можно реализовать в PHP:

```php
header("HTTP/1.1 301 Moved Permanently");
header("Location: http://example.com/newpage.html");
die;
```

Перенаправление можно реализовать в nginx

```nginx
location /old/url/ {
    return 301 /new/url;
}
```

###### Постоянные перенаправления

Постоянные перенаправления (*permanent redirection* [ˈpɜːmənənt rɪdɪˈrekʃn]) – означают, что запрошенный документ был окончательно перенесен на новый URI. Ответ с редиректом кешируется браузерами на бесконечный срок, если в заголовках кеширования не указано иное. Кеширование можно отключить или ограничить на определенное время с помощью заголовков Cache-Control или Expires.

Основной код для постоянного перенаправления – 301.

С точки зрения SEO:

- постоянное перенаправление сообщает поисковым роботам, что нужно объединить два разных адреса в один, где основным будет тот, на который и происходит перенаправление. 

- Ссылочный вес и показатели сайта передаются новому URL. 

- Поисковый робот может навсегда забыть о старом URL. 

- Исходный URL перестает отображаться в поиске

Пример использования:

- чтобы перевести пользователей с HTTP на HTTPS. 

Единственный способ отменить постоянный редирект, который закеширован в браузере многих пользователей, – сделать обратный редирект на исходный URL-адрес. В этом случае браузер заметит цикл и попробует снова обратиться по исходному URL.

301 Moved Permanently – постоянное перенаправление, по стандарту при перенаправлении браузер должен быть использовать тот же HTTP *method*, что и у первого запроса. Все браузеры нарушают стандарт и изменяют метод второго запроса на GET, несмотря на то, что первый запрос был с иным методом (чаще всего PUT). Поэтому в дополнение к 301 коду, введен 308 код. 

308 Permanent Redirect — постоянное перенаправление. Метод запроса (GET/POST) менять не разрешается. Например, POST запрос должен быть отправлен по новому URI тем же методом POST. Параметры исходного POST запроса из тела этого запроса, также подставляются браузером в POST-запрос по новому URI.

###### Временные перенаправления

Временные перенаправления (Temporary Redirect [ˈtemprəri rɪdɪˈrekʃn]) – запрошенный документ временно доступен по другому URI, указанному в заголовке Location. По умолчанию, ответ не кешируется, так как возможно в будущем либо ресурс станет снова доступен по исходному URI, либо изменится URI перенаправления в заголовке Location. Т.е. браузер должен по прежнему делать запрос на исходный URL.

Временное перенаправление кешируется, только если указаны заголовки кеширования Cache-Control или Expires.

С точки зрения SEO:

- не забывать и продолжать индексировать содержимое исходного URL

- Исходный URL остается в результатах поиска, отображаются оба URL – исходный и тот, на который редиректит.

Примеры использования:

- во время выполнения технических работ для переадресации на заглушку, чтобы после окончания работ отключить редирект

- так как временный редирект не кешируется, его можно использовать чтобы редиректить пользователей на разные страницы в зависимости от каких-то условий бинес-логики. Например:

    - по URI /lastPost редиректить на последний опубликованный пост

    - редиректить пользователей на различные языковые версии сайта, определяя геолокацию пользователя по IP. 

302 Found, 302 Moved Temporarily — временное перенаправление. Особенность: по стандарту при перенаправлении с 302 кодом браузер должен быть использовать тот же HTTP *method*, что и у первого запроса. Все браузеры нарушают стандарт и изменяют метод второго запроса на GET, несмотря на то, что первый запрос был с иным методом (чаще всего PUT). Поэтому в дополнение к 302 коду, введены коды 303 и 307. Поведение браузеров на ответы с кодами 303 и 307 соответвует стандарту и рекомендуется использовать именно эти коды.

303 See Other — временное перенаправление. Особенность: при перенаправлении нужно изменить метод второго запроса на GET, несмотря даже на то, что первый ресурс запрашивался другим методом.

Примеры применения:

- производится отправка веб-формы с даннами для поиска поста по его заголовку методом POST. Если обнаружен документ с введённым названием, то сервер отвечает кодом 303, указав в заголовке Location его постоянный адрес. Тогда браузер гарантировано его запросит методом GET для получения содержимого. В противном случае сервер просто вернёт клиенту страницу с результатами поиска. (Хотя на самом деле форма поиска должна отправляться методом GET, т.к. это *safe*-операция. И тогда все равно какой 3XX код использовать, т.к. исходный запрос GET, и редирект также GET).

- шаблон проектирования Post/Redirect/Get.

Цель шаблона: предотвратить повторную отправку веб-формы, когда пользователь выполнить Refresh страницы с отправленной формой. В итоге, например, могут быть созданы задвоенные документы. 

Способ решения: в ответ на POST запрос возвращается не 200 код, а 303 код с редиректом на страницу созданного документа. 

307 Temporary Redirect — временное перенаправление. Метод запроса не должен меняться. Например, POST запрос должен быть отправлен по новому URI тем же методом POST. Параметры исходного POST запроса из тела этого запроса, также подставляются браузером в POST-запрос по новому URI.

###### Другое

304 Not Modified — используется для ответа на условный GET с заголовками If-Modified-Since или If-None-Match, если контент не изменился, т.е. прошел валидацию.

| Постоянный (permanent) | Кешируется                | 301  | По стандарту:  тот же, что и у исходного запроса  Фактически:  всегда GET |

##### Ошибка клиента

400 Bad Request — сервер обнаружил в запросе клиента синтаксическую ошибку.

401 Unauthorized — для доступа к запрашиваемому ресурсу требуется аутентификация. Вместе с кодом 401 посылается заголовок WWW-Authenticate с указанием типа аутентификации (например, Basic) и зоны. Клиент повторяет запрос к ресурсу, включая в запрос заголовок Authorization с требуемыми для аутентификации данными. Если код 401 приходит в ответ на запрос с заголовком Authorization, значит для этих учетных данных было отказано в авторизации.

403 Forbidden — сервер понял запрос, но он отказывается его выполнять из-за ограничений в доступе для клиента к указанному ресурсу. Запрос не следует повторять.

404 Not Found – сервер понял запрос, но не нашёл соответствующего ресурса по указанному URL. Если серверу известно, что по этому адресу был документ, то ему желательно использовать код 410. Ответ 404 может использоваться вместо 403, если требуется тщательно скрыть от посторонних глаз определённые ресурсы

405 Method Not Allowed — указанный клиентом метод нельзя применить к текущему ресурсу. В ответе сервер должен указать доступные методы в заголовке Allow, разделенные запятой.

408 Request Timeout — время ожидания сервером передачи от клиента истекло. Клиент может повторить аналогичный предыдущему запрос в любое время. Например, такая ситуация может возникнуть при загрузке на сервер объёмного файла методом POST или PUT.

410 Gone — ранее по указанному URL существовал ресурс, но он был удалён и теперь недоступен. 

412 Precondition Failed — условные заголовки запроса If-Match, If-Unmodified-Since не соответствуют ресурсу, который хранится в настоящий момент по указанному URL. Ресурс скорее всего был модифицирован. 

414 URI Too Long — сервер не может обработать запрос из-за слишком длинного URI. Чаще всего ошибка возникает из-за слишком большой строки параметров при использовании метода GET.

##### Ошибка сервера

500 Internal Server Error — любая внутренняя ошибка сервера, которая не входит в рамки остальных ошибок класса

501 Not Implemented — сервер не поддерживает возможностей, необходимых для обработки запроса. Например, сервер не понимает указанный в запросе метод. 

502 Bad Gateway — сервер, выступая в роли шлюза или прокси-сервера, получил недействительное ответное сообщение от вышестоящего сервера

503 Service Unavailable — сервер временно не имеет возможности обрабатывать запросы по техническим причинам (обслуживание, перегрузка и прочее)

504 Gateway Timeout — сервер в роли шлюза или прокси-сервера не дождался ответа от вышестоящего сервера для завершения текущего запроса

#### Пояснение

Пояснение к коду состояния (*Reason Phrase*) —предназначено для упрощения чтения ответа человеком. Пояснение как правило не учитывает клиентским ПО и отличается у разных веб-серверов. 

### Общая структура

После стартовой строки следуют заголовки, а также тело ответа. Например:

```http
HTTP/1.1 200 OK
Server: nginx/1.2.1
Date: Sat, 08 Mar 2014 22:53:46 GMT
Content-Type: application/octet-stream
Content-Length: 7
Last-Modified: Sat, 08 Mar 2014 22:53:30 GMT
Connection: keep-alive
Accept-Ranges: bytes

Wisdom
```

 

Тело ответа следует через два переноса строки после последнего заголовка. Для определения окончания тела ответа используется значение заголовка Content-Length (в данном случае ответ содержит 7 восьмеричных байтов: слово «Wisdom» и символ переноса строки) или Transfer-Encoding в случае keep-alive соединений, если эти заголовки отсутствуют, то в конце ответа соединение должно быть закрыто.

Пример ответа с кодом 302 – перенаправление к ресурсу по другому адресу. Новый адрес указан в заголовке Location:

```http
HTTP/1.1 302 Moved Temporarily
Server: nginx
Date: Sat, 08 Mar 2014 22:29:53 GMT
Content-Type: text/html
Content-Length: 154
Connection: keep-alive
Keep-Alive: timeout=25
Location: http://habrahabr.ru/users/alizar/

<html>
...
</html>
```

## Заголовки

Заголовки HTTP (HTTP *Headers*) — это строки в HTTP-сообщении, содержащие разделённую двоеточием пару имя-значение. Заголовки идут сразу после стартовой строки запроса/ответа и оканчиваются двойным CR+LF.

Все заголовки разделяются на четыре основных группы:

- *General Headers* (основные заголовки) — используются в запросах и ответах, большинство из них являются обязательными (например, Date, Cache-Control).

- *Request Headers* (заголовки запроса) — используются только в запросах клиента.

- *Response Headers* (заголовки ответа) — используются только в ответах от сервера.

- *Entity Headers* (заголовки сущности) — сопровождают каждую сущность сообщения. Заголовки сущности могут быть использованы как заголовки отдельных сущностей в сообщениях с медиатипом multipart/*.

Именно в таком порядке рекомендуется размещать заголовки в сообщении. 

Все необходимые для функционирования HTTP заголовки описаны в основных RFC. Если не хватает существующих, то можно вводить свои. Традиционно к именам таких дополнительных заголовков добавляют префикс «X-» для избежания конфликта имён с возможно существующими.

Язык разметки HTML позволяет задавать необходимые значения заголовков HTTP внутри `<HEAD>` с помощью тега `<META>`. При этом название заголовка указывается в атрибуте http-equiv, а значение — в content. Например, всегда выставляется значение заголовка Content-Type с указанием кодировки:

```html
<meta http-equiv="Content-Type" content="text/html;charset=utf8">
```

 

 

### Date

Дата клиента или сервера на момент генерации пакета.

```http
Date: Tue, 15 Nov 1994 08:12:31 GMT
```

Время всегда указывается для часового пояса GMT (UTC+0), в PHP функция gmdate(). Эта дата берётся за отправную точку кешем для вычисления актуальности относительно текущего момента времени (с ней будут сравниваться даты из Expires и дата, полученная добавлением к Date количества секунд из Cache-Control: max-age).

### Host

*Request header*. Является обязательным с HTTP 1.1. Необходим для поддержки виртуального хостинга на сервере – указывает какой хост использовался в запросе(например, xxx.net или en.xxx.net). Так как фактически сетевое соединение во всех случаях открывается с одним IP адресом. При этом HTTP сервер не получает информацию о хосте из адресной строки браузера, т.к. преобразование доменного имени в IP-адрес осуществляется на стороне клиента и обращение идет уже по IP адресу. Поэтому клиент подставляет доменное имя в заголовок Host.

### Content-type

*Entity header*. По стандарту HTTP/1.1 любое сообщение, содержащее *entity-body* обязано включать заголовок Content-Type, определяющее формат сущности. Формат сущность определяется ее MIME-типом, либо используется термин «медиатип» (*media type*). 

Браузеры используют этот MIME-тип из заголовка Content-type с целью поиска подходящего приложения для просмотра данных (например, Acrobat для PDF). 

```http
Content-Type: text/plain
```

#### MIME

MIME [maim] (Multipurpose Internet Mail Extensions — многоцелевые расширения интернет-почты) —стандарт для форматирования информации с целью передачи по Интернету. 

MIME определяет механизмы для передачи любого типа информации по текстовому протоколу (которым является протокол HTTP): текст в многобайтовой кодировке, бинарные данные: картинки, музыка, фильмы. 

##### MIME-типы в форме HTML

По стандарту в HTML-формах могут использоваться следующие типы кодирования:

- application/x-www-form-urlencoded. По умолчанию. 

Данные передаются в теле запроса в формате, похожем на строку GET-запроса. Вместо файлов передается только название. Символы URL-кодируются. Формат неэффективен для передачи специальных символов, которые кодируются в %XX – размер данных увеличивается в несколько раз.

```text
param1=value1&param2=value2&file1=a.txt
```

- multipart/form-data. Необходимо явно использовать при наличии в форме `<input type="file">`. Данные передаются в теле запроса, формат описан ниже. Эффективен для передачи специальных символов, т.к. данные передаются в двоичном виде байт-в-байт. Неэффективен для передачи коротких сообщений, т.к. добавляет служебные заголовки и *boundary*.

- text/plain. Не используется из-за различной интерпретации браузерами.

##### MIME-типы multipart/*

Формат MIME поддерживает передачу нескольких сущностей в пределах одного сообщения. Причём сущности могут быть как в виде одноуровневой последовательности, но и в виде иерархии с вложением сущностей друг в друга. 

Если сущности выстроены в виде иерархии, то нелистовые узлы должны принадлежать одному из multipart/* медиатипов, а листовые узлы – не multipart/* медиатипу. 

Для передачи множественного сообщения в заголовок Content-Type добавляется параметр *boundary* [ˈbaʊndərɪ] (граница), который обозначает последовательность символов, разделяющих части сообщения. Клиент ([браузер](https://ru.wikipedia.org/wiki/Браузер)) генерирует эту последовательность случайно.

Пример отправки веб-формы с письмом со вложенными картинками:

```http
POST /send-message.html HTTP/1.1
...
Content-Type: multipart/form-data; boundary=Asrf456BGe4h

--Asrf456BGe4h
Content-Disposition: form-data; name="Address"

brutal-vasya@example.com
--Asrf456BGe4h
Content-Disposition: form-data; name="AttachedFile"; filename="horror-photo-1.jpg"
Content-Type: image/jpeg

(двоичное содержимое фотографии)
--Asrf456BGe4h--
```

Начало каждой части сообщения обозначается строкой --boundary. Конец последнего сообщения обозначается строкой --boundary--. В самом начале включаемой части располагаются заголовки, описывающие её содержимое (Content-Disposition, Content-Type). Могут использоваться *Entity Headers* (заголовки сущности). В заголовке Content-Disposition параметр name соответствует атрибуту name в `<input>`. Параметр filename соответствует исходному имени файла на компьютере пользователя.

За заголовком следует пустая строка, затем сами данные. Если не определён Content-Type, то он берётся по умолчанию — text/plain.

##### Формат MIME-типа

*Media type* содержит обязательно тип и подтип. Опционально могут быть указаны суффикс и параметры:

```text

```

Пример MIME-типа для HTML- файла в кодировке UTF-8. 

```text
text/html; charset=UTF-8
```

Здесь charset=UTF-8 является параметром.

Примеры суффиксов: +xml, +json

### Для управления кешированием

Про [общие принципы кеширования здесь](Highload.md#кеширование)

Заголовки `Expires` и `Cache-control` используются для указания срока свежести контента. Заголовки `Last-modified` и `Etag` называются валидаторами. Если в запросе нет хотя бы одного заголовка свежести и хотя бы одного заголовка-валидатора, контент не кешируется. 

##### Pragma

Описан в стандарте HTTP/1.0. В стандарте описано поведения только при использовании в запросе браузером в виде:

```http
Pragma: no-cache
```

В запросе имеет смысл аналогичный Cache-Control: no-cache – браузер сообщает серверу и прокси-кэшам, что хочет новую версию ресурса.

Его смысл в заголовке ответа в стандарте не указывается и поэтому браузеры должны его игнорировать. Поведение Pragma: no-cache в ответе специфично для реализации, хотя некоторые браузеры обращают внимание на этот заголовок в ответе. Заголовок использовался до появления Cache-Control в HTTP/1.1, имеет смысл использовать вместе с Cache-Control в целях совместимости с клиентами, поддерживающими только HTTP/1.0. 

##### Expires

Описан в стандарте HTTP 1.0 и гарантированно поддерживается всеми кешами, используется для обратной совместимости. cache-control имеет приоритет над expires. 

В значении указывается время, до которого контент трактуется как свежий. По истечении этого времени производится валидация контента. 

Корректным значением является HTTP-дата по Гринвичу (GMT) (не по местному часовому поясу):

```http
Expires: Thu, 31 Dec 2037 23:55:55 GMT
```

Некорректные значения интерпретируются как истекшие и контент не кешируется..

Недостатки:

- Часы веб-сервера и кэша должны быть синхронизированы, иначе, например, устаревший контент будет трактоваться как свежий.

- Если время в expires прописывается вручную, то можно забыть о необходимости его изменения и соответственно будет установлено время в прошлом, т.е. кеш отключен.

##### Cache-control

*General header*. Появился в версии HTTP 1.1. Самый главный заголовок кеширования. 

###### Заголовок запроса

Позволяет управлять кэшем клиенту.

```http
Cache-Control: no-cache
```

Клиент может использовать следующие директивы:

**no-cache** Кэш не должен использовать ответ для удовлетворения запроса без успешной ревалидации начальным сервером.. Chrome отправляет этот заголовок, когда в панели разработчика включена галочка «Disable cache».

**max-age = seconds** кэш должен быть не старше времени, которое указано в секундах. Частный случай max-age = 0 отключение кеширования. 

###### Заголовок ответа

Имеет приоритет над Expires. Пример:

```http
# запрет кэширования запроса
Сache-control: private, max-age=0, no-cache  

# кэширование результата запроса в браузере на 60 секунд
Cache-control: private, max-age=60
```

Его настройки называются директивами ответа кэша. Ниже основные директивы.

**public** – разрешает кэширование на публичных прокси-серверах 

**private** – кэширование будет работать только для браузера конкретного пользователя, например, имеет смысл на страницах после авторизации.

**no-cache** – необходимо отправить запрос на сервер для валидации ресурса перед использованием закешированных данных. Используется совместно с etag. Может применяться для контроля аутентификации запрашивающего контент клиента (особенно в случае кеширования страницы в *shared cache* при использованиис public смотреть ниже). Применяется для постоянного контроля свежести, при этом на каждый запрос контент не отсылается заново.

**no-store** – не сохранять ответ ни при каких условиях для безопасности секретной информации.

**max-age=[секунды]** – время в секундах, в течение которого контент остается свежим. Самое большое значение – год, или 31536000.

**s-maxage=[секунды]** – **s** означает *shared cache*, для общего кеша (*proxy*, CDN) эта директива имеет преимущество над max-age и expires.

**must-revalidate** – строго запрещает использовать протухший контент в кеше без запроса на валидацию, необходимо для критичных финансовых данных. Если ревалидация невозможна (при недоступности сервера), должна возвращаться ошибка. must-revalidate указывает строго выполнить ревалидацию для протухшего кеша, no cache – выполнять ревалидацию при каждом запросе. max-age=0, must-revalidate идентично no-cache.

**proxy-revalidate** - подобен must-revalidate, но применяется только к прокси.

**no-transform** – запрещает прокси изменять заголовки и контент для ускорения работы (изменять формат изображения, дописывать заголовки, менять их порядок).

##### Last-Modified

Валидатор, стандарт HTTP 1.0. Указывает время, когда контент был в последний раз именен. Используется поисковыми системами для отображения даты создания страницы.

```http
Last-modified: Fri, 1 Dec 2014 01:01:01 GMT
```

###### Заголовок запроса If-Modified-Since

Используется только для GET и HEAD. [If-None-Match](https://developer.mozilla.org/ru/docs/Web/HTTP/Headers/If-None-Match) более приоритетен.

Алгоритм:

- Если запрошенный объект **НЕ БЫЛ** модифицирован с даты If-Modified-Since, объект не будет прислан сервером, а в статус ответа – 304 Not modified без тела сообщения.

- Если запрошенный объект **БЫЛ** модифицирован с даты If-Modified-Since,  сервер обрабатывает запрос как обычно, как будто данный заголовок в запросе не указан.

Основной вариант применения: валидация контента совместно с Last-modified. Дату из заголовка Last-modified  браузер сохраняет и когда в следующий раз потребуется провалидировать контент, отправляет запрос с заголовком If-Modified-Since с указанием этой даты, как бы спрашивая, изменялся ли документ с тех пор:

```http
If-Modified-Since: Fri, 1 Dec 2014 01:01:01 GMT
```

Если файл не изменялся, сервер отправляет браузеру пустой ответ со статусом 304 (Not Modified) и экономит трафик. В этом случае, браузер знает, что файл не обновлялся и может отобразить копию, которую он сохранил в прошлый раз. 

Пример реализации:

```php
$modifiedDate = filemtime($filename);
 $HTTPdate = gmdate('D, d M Y H:i:s ', $modifiedDate) . 'GMT';
 $if_modified_since = $_SERVER['HTTP_IF_MODIFIED_SINCE'] ?? null;

 if($if_modified_since && $if_modified_since == $HTTPdate)
 {
   header('HTTP/1.1 304 Not Modified');
   exit();
 }
 else
 {
   header("Last-Modified: $HTTPdate");
 }
 # ниже формируем контент
```

Пример кеширования страницы в браузере на 10 минут:

```php
$if_modified_since = $_SERVER['HTTP_IF_MODIFIED_SINCE'] ?? null;

 if($if_modified_since && $if_modified_since < time() - 600) {
   header('HTTP/1.1 304 Not Modified');
   exit;
 }
```

###### Заголовок запроса **If-Unmodified-Since**

Алгоритм:

- Если запрошенный объект **НЕ** **БЫЛ** модифицирован с даты If-Unmodified-Since, сервер обрабатывает запрос как обычно, как будто данный заголовок в запросе не указан. 

- Если запрошенный объект **БЫЛ** модифицирован с даты If-Unmodified-Since, сервер не выполняет запрошенную отперацию, статус ответа –412 (Precondition Failed).

Основной вариант применения: для механизма оптимистичного контроля отсутствия конфиликтов при параллельном изменении контента для предотвращения перезаписи одних изменений другими. If-Unmodified-Since позволяет проконтролировать отсутствие изменений в контенте между моментами загрузки страницы и момент отправки формы с изменениями. Для этого к POST-запросу с данными формы присоединяется заголовок:

```http
If-Unmodified-Since: Wed, 21 Oct 2015 07:28:00 GMT
```

Запрос успешно обрабатывается сервером, только если объект не был модифицирован.

##### Etag

Etag (*entity-tag*) – валидатор, уникальный идентификатор, присвоенный веб-сервером на определенную версию ресурса, позволяющий сэкономить трафик. Введен в HTTP/1.1. 

Преодолевает недостатки Last-modified:

- Разрешение в одну секунду, а изменения могут происходить чаще.

- Может быть несколько допустимых версий контента

- Использование версии более удобно, чем даты.

Сравнение ETag имеет смысл только c Etag с одного и того же URL, идентификаторы, полученные из разных URL-адресов никак несвязаны. 

###### Генерация ETag

Имеет вид произвольной строки, которая начинается и заканчивается символом двойной кавычки (“). Браузер сравнивает строки функцией вроде strcmp().

```http
ETag: "d41d8cd98f00b204e9800998ecf8427e"
```

Метод генерации ETags в стандарте не указан, например, это может быть хэш последнего времени изменения, содержания файла или даже только номер версии.

Веб-сервера могут автоматически генерировать ETag и Last-Modified заголовки для статического контента. Для большей совместимости иногда применяют оба валидатора. Для динамического контента генерация выполняется вручную, т.к. отсутствует статический файл, для которого можно было бы рассчитать хеш.

###### Сильный (*strong*) и слабый (*weak*) ETag

Различают сильный (*strong*) и слабый (*weak*) ETag. К слабому ETag спереди за пределами кавычек дописывается W/:

```http
ETag: W/"d41d8cd98f00b204e9800998ecf8427e"
```

Сильный ETag гарантирует, что контент с одним и тем же ETag идентичен байт-в-байт, тогда как слабый ETag просто обещает «семантическую эквивалентность», т.е. возможны разные варианты контента с одним Etag, идентичные по смыслу. Контент с сильным ETag браузер может загружать по частям в случае проблем. Контент с слабым ETag может иметь даже разный размер.

Как правило, сильный Etag используется для статического контента, где структура файла измениться не может. Слабый – для динамически генерируемого контента. Например, в конце HTML-кода страницы выводится время генерации в миллисекундах и имя ответившего сервера (например, dynamic4). Если кроме этих значений содержание страницы не меняется, то можно разным вариантам страницы присвоить одинаковый слабый Etag, хотя в этом случае содержимое страницы меняется в нескольких символах и может иметь разное количество символов, если, например, время генерации меняется (1,3 с – 2,456 с).

###### Заголовок запроса If-None-Match

Более приоритетен, чем If-Modified-Since.

Алгоритм обработки сервером:

- Если значение в If-None-Match **СООТВЕТСТВУЕТ** ETag объекта или указана «*» и объект **СУЩЕСТВУЕТ**, запрошенное действие не исполняется. Для методов GET и HEAD возвращается 304 (Not Modified). Для других методов возвращается код 412 (Precondition Failed).

- Если значение в If-None-Match **НЕ** **СООТВЕТСТВУЕТ** ETag объекта или указана «*» и объект **НЕ СУЩЕСТВУЕТ**, сервер обрабатывает запрос как обычно, как будто данный заголовок в запросе не указан.

Варианты применения:

**Алгоритм валидации закешированного контента**

Алгоритм валидации с использованием Etag:

- вместе с контентом клиенту отправляется заголовок ETag

- клиент кэширует контент вместе с его ETag. 

- если клиент хочет получить страницу с того же адреса, он пошлет сохраненное значение ETag вместе с запросом в поле If-None-Match.

```http
If-None-Match: "d41d8cd98f00b204e9800998ecf8427e"
```

- сервер сравнивает ETag клиента с ETag для текущей версии ресурса. Если значения ETag совпадают, это означает, что ресурс не изменился, сервер может отправить обратно очень короткий ответ с HTTP статусом 304 Not Modified. Статус 304 сообщает клиенту, что его кэш версия по-прежнему актуальна и что он должен использовать её.

Однако, если ETag-значения не совпадают, то есть ресурс изменился, то полный ответ, в том числе содержание ресурса, возвращаются, как будто ETag не использовался. В этом случае клиент может принять решение о замене в кэше версии ресурса на вновь возвращенную и новый ETag.

Пример реализации:

```php
$eTag = md5($content);
 header('ETag: "'.$eTag.'"');
 $if_none_match = $_SERVER['HTTP_IF_NONE_MATCH'] ?? null;

 if($if_none_match && $if_none_match == $eTag)
 {
   header('HTTP/1.1 304 Not Modified');
   exit();
 }

 # ниже формируем контент
```

Браузер может хранить несколько версий контента с разными Etag и указать это в запросе: 

```http
If-None-Match "abc", "def"
```

Если одна из версий является корректной, сервер ответит кодом «304 Not Modified», обязательно с указанием ETag версии, которую является корректной. 

**Контроль отсутствия объекта при загрузке**

Используя 

```http
If-None-Match: *
```

совместно с методом PUT можно при сохранении файла гарантировать, что не был ли ранее загружен файл с таким же именем. 

###### Заголовок запроса If-Match

Позволяет проверить, что объектов не изменялся. Алгоритм обработки сервером:

- Если значение в If-Match **СООТВЕТСТВУЕТ** ETag объекта или указана «*» и объект **СУЩЕСТВУЕТ**, сервер обрабатывает запрос как обычно, как будто данный заголовок в запросе не указан.

- Если значение в If-Match **НЕ СООТВЕТСТВУЕТ** ETag объекта или указана «*» и объект **НЕ СУЩЕСТВУЕТ**, запрошенное действие не исполняется и возвращается код 412 (Precondition Failed).

Вариант применения: для механизма оптимистичного контроля отсутствия конфиликтов при параллельном изменении контента для предотвращения перезаписи одних изменений другими. ETag позволяет проконтролировать отсутствие изменений в контенте между моментами загрузки страницы и момент отправки формы с изменениями. Для этого к POST-запросу с данными формы присоединяется заголовок:

```http
If-Match: "d41d8cd98f00b204e9800998ecf8427e"
```

Если на сервере выясняется, что контент изменялся после отдачи Etag, возвращается [412](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/412) Precondition Failed.

###### Заголовок запроса If-Range

Используется совместо с заголовком Range для получения части контента или всего контента целиком, если он изменялся. Значением является ETag или HTTPDate

```http
If-Range: (Etag | HTTPdate)
```

Алгоритм обработки сервером:

- Если значение в If-Range **СООТВЕТСТВУЕТ** ETag объекта, то возвращается часть объекта с кодом [206](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/206) Partial Content.
- Если значение в If-Range **НЕ СООТВЕТСТВУЕТ** ETag объекта, то возвращается весь объект с кодом [20](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/206)0 ОК.

###### Фишки

ETags может быть использован по принципу Cookie для идентификации клиентов и их сессий, если Cookie клиента отключены. Сервер может отсылать каждому клиенту уникальный ETag, подобно уникальной куке сессии. При очередном запросе страницы на сервер будет выслана это уникальное значение Etag, по которому сервер может идентифицировать клиента. 

##### Vary

Используется, если одному URL соответствует несколько вариантов содержимого и их можно различить по какому-то заголовку. 

Примеры:

- Одна страница имеет две языковые версии, которые должны храниться отдельно в кеше браузера. 

- В прокси-кэше нужно хранить отдельно сжатую (gzip) и несжатую версии для устаревших клиентов.

Заголовок Vary позволяет сообщить кэшу названия тех заголовков запроса, по которым необходимо различать разные варианты контента. Использовать значение в кеше можно только при совпадении всех полей из заголовка Vary закешированном и новом запросе. Если рассматривать кэш как хранилище данных вида ключ (URL)-значение (content), то значения заголовков из Vary присоединяются к ключу (URL+Vary). 

Например, если отображение страницы зависит от браузера (разные CSS для разных браузеров) и того, поддерживает ли он gzip-сжатие:

```http
Vary: Accept-Encoding, User-Agent
```

Для разных сочетаний значений заголовков, перечисленных в Vary,необходимо генерировать различные значения ETag.

## Механизмы

### Скачивание по частям

Пусть сервер возвращает в ответе заголовок Accept-Ranges:

```http
HTTP/1.1 200 OK
Content-Length: 160993792
Accept-Ranges: bytes
...
```

Заголовок Accept-Ranges информирует клиента о том, что он может запрашивать у сервера фрагменты, указывая их смещения от начала файла в байтах.

Исходя из значения заголовка Content-Length, менеджер закачек может поделить весь объём на равные фрагменты и запросит их по отдельности, организовав несколько потоков.

Запрос с указанием выдать содержимое с некоторого смещения должен включать заголовок Range:

```http
GET /conf-2009.avi HTTP/1.0
Range: bytes=88080384-
...
```

Сервер в ответ возвращает фрагмент и сопровождает фрагмент кодом 206 (Partial Content). 

```http
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 88080384-160993791/160993792
Content-Length: 72913408
```

В заголовке Content-Range содержится информация о данном фрагменте: номера начального и конечного байта, а после слэша — суммарный объём всего файла в байтах. В заголовке Content-Length указан размер передаваемого фрагмента.

### Согласование содержимого

Согласование содержимого (*Content negotiation* [ˈkɔntent nɪgəʊʃɪˈeɪʃn]) — механизм автоматического определения необходимого ресурса при наличии нескольких разнотипных версий документа. 

Различают два основных типа согласований:

- Управляемое сервером (*server-driven*).

- Управляемое клиентом (нгл. *Agent-Driven*).

Одновременно могут быть использованы оба типа или каждый из них по отдельности.

Также в RFC определено прозрачное согласование (*Transparent negotiation* [trænsˈpærənt nɪgəʊʃɪˈeɪʃn]) как предпочтительный вариант комбинирования обоих типов.

Управляемое сервером

При наличии нескольких версий ресурса сервер может анализировать заголовки запроса клиента, чтобы выдать, по его мнению, наиболее подходящую. В основном анализируются заголовки Accept, Accept-Charset, Accept-Encoding, Accept-Languages и User-Agent (это все *Request Headers*, которые позволяют указать клиенту, что он поддерживает). 

Серверу желательно включать в ответ заголовок Vary с указанием параметров, по которым различается содержимое по запрашиваемому URI.

Также может учитываться географическое положение клиента, которое можно определить по его IP-адресу.

Управляемое клиентом

Тип содержимого определяется на стороне клиента. Для этого сервер возвращает ответ с кодом состояния 300 (Multiple Choices) или 406 (Not Acceptable), а в теле ответа – список возможных вариантов страницы. Затем клиенту нужно сделать дополнительный запрос, для получения выбраного варианта. 

Прозрачное согласование

Согласование, прозрачное для клиента и сервера. В некотором общем кэше содержится набор всех возможных вариантов страницы и кеш сам делает выбор нужного варианта.

### HTTP аутентификация

#### Basic-аутентификация

Basic-аутентификация – механизм для клиента-HTTP (например, веб-браузер) для предоставления имени пользователя и пароля при выполнении запроса. Basic-атентификация является самым простым способом обеспечить аутентификацию пользователей, так как не использует cookie, идентификаторы сессий, не требует создание страниц авторизации.

После ввода имени пользователя и пароля веб-браузер кэшировать эти данные в течение некоторого периода времени, т.к. их требуется подставлять в заголовок каждого HTTP-запроса. 

Если требуется заставить браузер «разавторизовать» пользователя и удалить закешированные аутентификационные данные, необходимо отправить в браузер заголовок 401 Unauthorized.

Протокол аутентификации

Если сервер требует аутентификации клиента для доступа к некоторому ресурсу, сервер возвращает ответ вида:

```http
HTTP/1.0 401 Unauthorized
WWW-Authenticate: Basic realm="My Realm"
Текст, который показывается, если пользователь нажал кнопку Cancel
```

Заголовок WWW-Authenticate указывает метод аутентификации (Basic) и название защищенной области (*realm*). Предполагается, что страницы с одинаковым *realm* используют одни и те же учетные данные. Некоторые браузеры в окне авторизации выводят название защищенной области из атрибута *realm*.

При получении такого ответа на запрос браузер отображает окно аутентификации и требует от пользователя ввести учетные данные. 

После того как пользователь указал «Имя» и «Пароль» и нажал кнопку «Войти», браузер кеширует эти данные и использует их для формирования заголовка запроса Authorization. Заголовок Authorization отправляется при каждом запросе к данному хосту. После нажатия кнопки «Войти» происходит запрос по первоначальному URI, только уже с указанием заголовка Authorization.

Алгоритм формирования заголовка Authorization:

1. Соединить имя пользователя и пароль символом : – Имя:пароль
2. Закодировать получившуюся строку в Base64: QWxhZGRpbjpPcGVuU2VzYW1l
3. Добавить к заголовку название метода аутентификации и пробел ("Basic ")

В итоге получаем такой заголовок:

```http
Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l
```

Реализация в PHP

При получении заголовка Authorization в запросе PHP устанавливает следующие элементы суперглобального массива $_SERVER:

- PHP_AUTH_USER – логин

- PHP_AUTH_PW – пароль

- AUTH_TYPE – тип аутентификации

Ниже пример программы, которая проверяет наличие учетных данных в запросе. Если учетных данных нет ­ возвращает 401 Unauthorized, иначе выводит учетные данные.

```php
if (!isset($_SERVER['PHP_AUTH_USER'])) {
   header('WWW-Authenticate: Basic realm="My Realm"');
   header('HTTP/1.0 401 Unauthorized');
   echo 'Текст, который показывается, если пользователь нажал кнопку Cancel';
   exit;
 } else {
   echo "Login: ".$_SERVER['PHP_AUTH_USER'];
   echo "Password: ".$_SERVER['PHP_AUTH_PW'];
 }
```

 

Указание логина и пароля в адресной строке

Можно указать login:password явно в адресной строке браузера и избежать открытия окна для ввода логина и пароля:

```text
http://login:password@host/path
```

#### Digest авторизация

Структура заголовка запроса пароля похожа

```php
<?php
 $realm = 'Запретная зона';

 if (empty($_SERVER['PHP_AUTH_DIGEST'])) {
   header('HTTP/1.1 401 Unauthorized');
   header('WWW-Authenticate: Digest realm="'.$realm.
      '",qop="auth",nonce="'.uniqid().'",opaque="'.md5($realm).'"');

   die('Текст, отправляемый в том случае, если пользователь нажал кнопку Cancel');
 }
```

Проверка ответа более сложная, с вычислением md5 хешей по данным.

 

## Протокол HTTPS

HTTPS (HyperText Transfer Protocol Secure) –расширение HTTP, которое реализует упаковку передаваемых данных в криптографический протокол SSL или TLS. Порт по умолчанию – 443.

## Протокол Websocket

Позволяет передавать данные в нужный момент, без отправки дополнительных HTTP-запросов. Стандартное «рукопожатие» (*handshake*) сводится к отправке HTTP-запроса с заголовком Upgrade, имеющим значение «websocket», на который сервер возвращает ответ с состоянием «101 Switching Protocols», и далее любая сторона может начать передавать данные уже по протоколу WebSocket.

## Постоянное соединение (keep-alive)

Постоянное HTTP-соединение (HTTP *persistent connection*, HTTP keep-alive, повторное использование соединений HTTP, HTTP *connection reuse*) — использование одного TCP-соединения для отправки и получения многократных HTTP-запросов/ответов вместо открытия нового соединения для каждого запроса/ответа. Протокол HTTP/2 расширяет эту идею, позволяя параллельные многократные запросы/ответы в одном соединении.

Преимущества:

- значительно ускоряет взаимодействие по HTTPS, которое требует существенны затрат на установку соединения. 

- смягчает ограничение количества соединений к одному хосту в браузерах. Изначально RFC ограничивало  количество постоянных соединений браузером к одному серверу значением 6, в более позднем [RFC](https://tools.ietf.org/html/rfc7230) для ускорения загрузки использована формулировка для клиента «использовать благоразумное количество одновременных соединений». На сегодня браузеры имеют следующие ограничения: FIrefox, Chrome - 6, Safari -4, IE- 8.

Настройка в nginx

### HTTP 1.0

В протоколе HTTP 1.0 нет официальной спецификации на работу с Keep-alive. Но формально они поддерживались как дополнение. Для включения данного режима браузер посылал в запросе заголовок:

```http
Connection: Keep-Alive
```

Сервер также возвращает ответ с заголовком:

```http
Connection: Keep-Alive
```

После этого соединение остаётся открытым. Клиент и сервер взаимодействуют в режиме запрос/ответ через то же соединение. Соединение закрывается по инициативе клиента или сервера при завершении обмена.

### HTTP 1.1

В HTTP 1.1 все соединения считаются постоянными, передача заголовка Connection: Keep-Alive не требуется. Время ожидания по умолчанию для Apache 2.4 только 5 секунд, что позволяет долго не блокировать потоки в ожидании. 

### Реализация в библиотеке curl

Curl сам держит пул постоянных соединений для каждой пары host:port, самостоятельно переоткрывает закрытые соединения и закрывает соединение при завершении скрипта. Т.е. в примере ниже соединение будет открываться только один раз:

```php
$ch = curl_init();
for ($i = 0; $i < 10; $i++) {
    curl_setopt_array($ch, [...]);
    $resp = curl_exec($ch);
}
```

## REST

REST (*Representational State Transfer* [ reprɪzənˈteɪʃnəl steɪt ˈtrænsfɜː ] – передача состояния представления) — архитектура взаимодействия распределенных компонентов в сети. Архитектура описывается в виде набора требований. API-интерфейсы веб-сервисов, которые соответствуют требованиям REST , называются RESTful API. 

Официального стандарта RESTful API не существует, однако реализации приложений используют множество стандартов: HTTP, URL, JSON….

Как правило «REST-запрос» представлять собой обычный HTTP-запрос. API-интерфейсы RESTful на основе HTTP определяются со следующими компонентами:

- базовый URL-адрес , например `http://api.example.com/resources`;

- *media type* ответов сервера (например, application/xml). 

- тип операции в запросе определяется через *method*, как правило используются следующие CRUD *methods*: GET, POST, PUT, DELETE. Данные передаются в качестве параметров запроса.

Cледующей таблице показано, как HTTP-методы обычно используются в RESTful API:

### Связь с HTTP *method*

Cледующей таблице показано, как HTTP-методы обычно используются в RESTful API:

| **HTTP methods** | **Коллекция, например ссылка    http://api.example.com/****posts/** | **Элемент, например ссылка    https://api.example.com/****posts/123** |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| GET              | Список  элементов коллекции: URI и другие сведения           | Получить представление  члена в соответствующем *media type*   |
| PUT              | Замените всю  коллекцию другой коллекцией.                   | Заменить элемент  коллекции, а если он не существует – создать его |
| PATCH            | Обычно не  используется                                      | Обновить отдельные  части элемента коллекции. В запросе указывается какое изменение произвести (replace, add, remove...). |
| POST             | Создать новый  элементв коллекции. URI нового элемента формируется автоматически и  возвращается в ответе. | Обычно не  используется. Иногда используется для обращения к элементу как к  самостотельной коллекции и создания новой записи внутри этого элемента. |
| DELETE           | Удалить всю  коллекцию                                       | Удалите элемент  коллекции                                   |

Метод GET является безопасным методом (или *нульпотентным* ), методы PUT и DELETE являются *идемпотентными*.

### Требования REST

Существует шесть обязательных требования к распределённому REST-приложению:

1. Модель клиент-сервер. За счет этого обеспечивается слабое зацепление компонентов приложения. Это дает преимущества слабого зацепления (смотреть Зацепление). Для REST особенно важной является возможность параллельной раработки серверной части и раличных клиентских частей – браузерного приложения, приложений для Windows, Android, Apple.
2. Отсутствие состояния у протокола взаимодействия (*stateless protocol* [ˈsteɪtləs ˈprəʊtəkɔl]) – между запросами клиента никакая информация о состоянии клиента на сервере не хранится. Т.е. сервер должен получить всю необходимую информацию для выполнения запроса из самого запроса. Состояние сессии хранится на стороне клиента.

Когда у клиента возникает необходимость перейти в новое состояние, клиент инициирует запрос к сереверу. В запросе он указывает тип операции (например, GET) и ресурс (на основе гипермедиа полученного из предыдущих запросов, например гиперссылка /post/1). Во время обработки запроса к серверу клиент находится в переходном состоянии.

3. Кэширование. Взаимодействующие клиент и сервер, а также промежуточные узлы, могут выполнять кэширование ответов сервера. Ответы сервера должны содержать заголовки, указывающие воможность кеширования и время кеширования.
4. Единообразие интерфейса. 

Унифицированный интерфейс предполагается следующее: 

    - любой ресурс можно идентифицировать по уникальному пути, как правило URI;
    
    - вся необходимая информация для выполнения запроса может быть получена из самого запроса;
    
    - клиенты хранят представления (Representational), из которых они могут извлечь информацию для манипуляции исходными ресурсами. 
    
    - HATEOAS (подробнее HATEOAS). 

5. Слоистость. Между клиентом и сервером могут размещаться промежуточные слои. Промежуточные слои могут выполнять кеширование, распределение нагрузки и др. 
6. Загрузка кода в клиент по требованию. Функциональность клиента может быть расширена путем загрузки в него скриптов (например, Javascript) с сервера. 

### HATEOAS

HATEOAS (*Hypermedia as the Engine of Application State*, гипермедиа как движок состояния приложения) –требование к архитектуре REST.

Клиент знает только некоторое количество точек входа в приложение (например, API список постов на главной странице). Дальнейшую информацию о доступных ресурсах и доступных операциях над ними клиент получает из результатов запросов, заранее не знает о них (например, конкретные посты и возможные операции над ними). Эти  действия динамически определяются на сервере и встраиваются в ответы как гипермедиа (к примеру, гиперссылки в гипертексте). Таким образом RESTful API не имеет строгого интерфейса, а взаимодействие выполняется через гипермедиа.

Пример RESTful ответа от банковского приложения в формате XML:

```http
HTTP/1.1 200 OK

Content-Type: application/xml

Content-Length: ...
```

 

```xml
<?xml version="1.0"?>

<account>

  <account_number>12345</account_number>

  <balance currency="usd">100.00</balance>

  <link rel="deposit" href="https://bank.example.com/accounts/12345/deposit" />

  <link rel="transfer" href="https://bank.example.com/accounts/12345/transfer" />

</account>
```

В зависимости от типа счета и уровня доступа, гипермедиа в ответе могут меняться.
