# Базовые термины

| Термин                 | Что означает                                                 |
| ---------------------- | ------------------------------------------------------------ |
| **Producer**           | Приложение, которое отправляет сообщения в Kafka.            |
| **Consumer**           | Приложение, которое читает сообщения из Kafka.               |
| **Message / Record**   | Сообщение: содержит значение (*value*), необязательный ключ (*key*), время и заголовки (*headers*). |
| **Topic**              | Именованный поток сообщений, например `orders` или `payments` (очередь с названием) |
| **Partition**          | Часть топика, в которой сообщения хранятся последовательно. Порядок гарантируется внутри одной *partition*'и. |
| **Offset**             | Позиция сообщения внутри *partition*.                        |
| **Broker**             | Сервер Kafka, который хранит сообщения и обслуживает запись и чтение. |
| **Cluster**            | Группа брокеров, работающих вместе.                          |
| **Consumer group**     | Группа *consumer*'s, которые распределяют между собой *partition*'s топика. Внутри группы одну *partition*'ю одновременно читает один consumer. |
| **Consumer lag**       | Отставание consumer от конца *partition*'и, обычно измеряется количеством сообщений. |
| **Commit offset**      | Сохранение позиции чтения, с которой *consumer* сможет продолжить работу после перезапуска. |
| **Replication factor** | Количество копий каждой *partition*'и на разных брокерах.    |
| **Leader / Follower**  | Leader обслуживает операции с *partition*'ей; *follower*'s копируют её данные. |
| **Retention**          | Правила хранения сообщений: например, удаление по возрасту или объёму. Прочитанные сообщения не удаляются сразу. |
| **Rebalance**          | Перераспределение *partition*'s между *consumer*'s в группе при изменении её состава. |

# Topic

*Topic* состоит из одной или нескольких ***partition*'s**. Каждая *partition* — последовательный журнал, в конец которого добавляются сообщения:

```
Topic: orders
├── Partition 0: [offset 0] [offset 1] [offset 2]
├── Partition 1: [offset 0] [offset 1]
└── Partition 2: [offset 0] [offset 1] [offset 2] [offset 3]
```

*Offset* уникален только внутри своей *partition*'и. Поэтому позицию сообщения определяют три значения: **topic + *partition* + offset**.

# Partition

*Partition*'s нужны для распределения нагрузки: их можно хранить на разных брокерах и читать параллельно.

Число *partition*'s ограничивает количество *consumer*'s, которые могут одновременно читать этот *topic* в одной *group*.

У сообщения может быть ключ — **key**, например `order_id`.

*Producer* использует ключ, чтобы выбрать *partition*. При неизменном количестве *partition*'s сообщения с одинаковым ключом попадают в одну *partition*. Это позволяет последовательно отправлять сообщения, относящиеся к одной сущности, например, заказ:

```
key = order-123:
заказ создан → заказ оплачен → заказ отправлен
```

Kafka сохраняет порядок **внутри каждой *partition*'и**. Общего порядка между всеми *partition*'s топика нет.

Если события одного заказа попали в разные *partition*'s, нельзя рассчитывать, что *consumer* прочитает их в нужной последовательности. Поэтому *key* часто выбирают по сущности, порядок событий которой важен: `order_id`, `user_id`, `account_id`.

Распределение по *partition*'s идёт по ключу: `partition = hash(key) % partitions` . Как только вы меняете *partition*'s , формула меняется — и сообщения с тем же *key*, которые раньше шли в *partition* A, начнут попадать в *partition* B. Старые записи остаются в A, новые ложатся в B. 

Глобальный (per-key) порядок при этом нарушается: события одной сущности могут обработаться вперемешку. Безопасно увеличивать число партиций можно либо при дизайне топика заранее (с запасом), либо остановив *producer*'ов и дождавшись полной вычитки уже накопленных сообщений перед переключением. 

ЧАСТАЯ ОШИБКА Считать, что добавление *partition*'s "на лету" безболезненно и автоматически ускоряет обработку. На деле оно ломает per-key ordering и не перераспределяет уже лежащие в старых партициях сообщени

# Consumer

Один *consumer* может читать несколько партиций. Позиция чтения отслеживается отдельно для каждой:

```
Consumer A:
  partition 0 → следующая позиция 125
  partition 1 → следующая позиция 87
```

# Offset

Важно различать две позиции:

- **Текущая позиция** — *offset* следующего сообщения, которое consumer получит будет читать дальше в текущем (!!!) запуске.
- **Committed offset** — сохранённый *offset*, откуда *group* сможет продолжить после перезапуска или передачи партиции другому *consumer*.

Новая *consumer group* будет читать *topic* с начала, а старая продолжит с *committed offset*.

# Consumer group

*Consumer group* — группа потребителей

*Consumer group* — *consumer*'s с одинаковым `group.id`, которые вместе читают топики.

Kafka назначает каждую *partition* **ровно одному consumer внутри группы**. Это распределяет работу.

Поэтому при 3 *partition*'s полезную работу делают максимум 3 *consumer*'а. Четвёртый войдёт в *consumer group*, но при rebalance не получит ни одной партиции и будет простаивать как горячий резерв (он подхватит *partition*, если один из активных *consumer*'ов отвалится). Число *consumer*'ов в *group* разумно держать <= числу *partition*; чтобы масштабироваться дальше, нужно увеличивать число *partition*, а не *consumer*'ов. 

Например, если у *topic* - 4 *partition*, то возможны распределения в зависимости от количеста *consumer*'s внутри *consumer group*:

| Consumers в группе | Распределение                     |
| ------------------ | --------------------------------- |
| 1                  | Читает все 4 партиции             |
| 2                  | Обычно по 2 партиции              |
| 4                  | По 1 партиции                     |
| 6                  | 4 читают, 2 остаются без партиций |

Например, для *group* из 2 *condumer*'s:

```
Group: warehouse
  Consumer A ← partition 0, partition 1
  Consumer B ← partition 2, partition 3
```

Каждая *consumer group* читает из *topic*'ов независимо (как отдельные сервисы на одном *databus*).

Если *warehouse* и *analytics* должны получить все события, им нужны разные `group.id`:

```
                     Topic orders
                     /          \
                    /            \
       Group: warehouse       Group: analytics
       A ← partitions 0, 1    C ← partitions 0, 1, 2, 3
       B ← partitions 2, 3
```

Каждая *group* хранит собственные *committed offset*'s. *Warehouse* может быть на offset `500`, а *analytic*'s — на `300` в той же партиции.

Если случайно дать *warehouse* и *analytics* одинаковый `group.id`, они начнут делить *partition*'s между собой: каждый сервис получит лишь часть событий.







# Durability

Каждая *partition* может иметь несколько копий на разных брокерах. Например, `replication factor = 3` означает три копии каждой *partition*'и, включая основную.

Количество *partition*'s отвечает за распределение нагрузки, а количество реплик — за устойчивость хранения к сбоям.
